# ADR 0025: One-way Shift transfer before execution

Status: Accepted implementation decision; **P4.11 DONE/CLOSED** at `b82dda89374ed9b4182630de4991b0d1569b8ae8`. F01/F02/F03 CLOSED, targeted APPROVE, 177 PASS / 0 QUALIFIED / 0 FAIL, SECURITY APPROVE and green [exact-commit CI 38125193187](https://github.com/RobinBrohl/storeos/actions/runs/38125193187); no active remediation. P4.12 remains UNSELECTED.

StoreOS needs a consented transfer of one complete future published Shift. Published ownership and original Task identities are evidence. Reassigning either in place would erase who originally received the work and make historical consent ambiguous.

Workforce owns the append-only proposal and durable command receipts. Tasks owns append-only source/replacement Task correspondence. An application coordinator uses public People, Identity, Organization, Workforce, Tasks, Knowledge and Merchandising ports inside the existing authorized Company transaction. It never reads a foreign repository or table. There are no asynchronous consumers, events, notifications, scheduler expiry, swaps, partial transfers, availability calendar or configurable roles.

A proposal captures the exact Shift/version, employee identities, interval, Account/link identities and Account versions. Source Task snapshots already retain exact ordered Template selections and Knowledge/Planogram pins; instruction bodies stay with their owners. Account versions conservatively fence changes to rights/activation and prevent a later return to the old role or active state from reviving the proposal. Link revocation/replacement also invalidates that basis. A newly linked recipient Account may read participant history but cannot inherit or replay the old recipient's consent. The current source identity can explicitly close stale work; an independent manager can reject it.

The request lifecycle is proposed → accepted → approved, with decline, source withdrawal, accepted-recipient withdrawal and manager rejection as terminal alternatives. Acceptance evidence remains after withdrawal/rejection. Time or eligibility changes only make reads non-actionable; an explicit withdrawal/rejection is needed to free the active-source slot. Withdrawal and rejection require 1–500 Unicode code points of trimmed plain text. Decline and proposal collect no personnel note.

Approval requires transfer management, Shift management and Task read capabilities, configured Location scope, and an Account different from the proposing and accepting Accounts. Current authorization and resource scope precede receipt lookup. Company + operation UUID binds actor, Location, request, kind, expected version and canonical payload. Exact committed replay returns the original result before fresh business validation; failure stores no receipt. The database protects immutable receipts and terminal evidence.

Approval rechecks captured identity/version, future interval using database `clock_timestamp()`, pristine source Tasks, current assignments and links, recipient overlap and exact guidance eligibility. It checks time again immediately before effects. Through owner ports it cancels original work, creates a new Shift for the named recipient with the exact interval/selections, materializes new pristine Tasks, records complete one-to-one lineage, publishes replacement work and commits request, receipt and audit atomically. No retained pin is upgraded. The existing deferred database constraint verifies the complete approval-time effect and exact snapshot correspondence, then checks authoritative wall-clock time is still strictly before captured startsAt at the final fresh-approval boundary. Crossing that boundary rolls back every effect with the existing `shift_not_transferable` error. Historical receipt replay performs no request UPDATE and does not reapply this fresh-approval invariant. The guard does not restrict later ordinary replacement execution or global Shift publication.

Migration 0023 adds three tables and two narrowly scoped existing-table unique anchors. The Account/link anchor binds both identities and Company/Location. The Task anchor binds identity, Shift, Company/Location and exact Template revision/position. Existing rows and migrations 0001–0022 remain unchanged. Runtime grants allow SELECT/INSERT and only request lifecycle UPDATE columns, with no DELETE/TRUNCATE, receipt/lineage UPDATE or SECURITY DEFINER functions.

Transfer history exposes colleague names, exact interval, task titles/pins, consent/decision evidence and lineage. It omits instruction bodies and execution values. Lineage never grants ordinary replacement access to the source. Replacement work executes through existing Guided Work. Transfer audit includes identifiers and state/version metadata; user reasons stay in request/receipt evidence and are not duplicated into audit/logs.

Flutter holds a session-bound immutable pending command for uncertain outcomes and allows exact retry only. Confirmed command evidence remains distinct from freshly fetched current detail. Failed refresh clears actionable detail. Every opaque session replacement, including the same Account, clears forms, cursors, cached evidence and pending commands and fences delayed replies.

Validation uses disposable isolated PostgreSQL, observed Company lock queues in both orders, injected stage failures, populated migration rollback/preservation, encrypted backup/restore, update/recovery, Flutter controllers and Chrome.
