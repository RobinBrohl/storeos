# Task-aware encrypted backup/restore acceptance

This runbook describes the automated acceptance that proves an encrypted
StoreOS PostgreSQL backup restores the complete employee-journey evidence.
It complements the crypto-format checks in [Test-BackupCrypto.ps1](Test-BackupCrypto.ps1)
and the operator commands in the [backup README](README.md); it does not
replace the operator restore process.

## Purpose

The acceptance seeds an isolated database with the bounded journey (company,
location, employee, account link, three published tasks in one shift), exercises
real numeric and confirmation work, approves a plugin and leaves an admin
session active. It then runs the real encrypted backup and isolated restore
scripts and proves that:

- row counts and canonical content hashes match for `shifts`,
  `task_template_revisions`, `task_instances`, `task_step_results`,
  `task_numeric_attempts`, `task_blockings`, `task_execution_commands` and
  `audit_entries`;
- identity sequence state for `audit_entries_id_seq` and `plugin_inbox_id_seq`
  matches;
- the source database is unchanged by backup and restore;
- the restored database has no active sessions and no active plugin tokens, and
  the restricted runtime role is denied both by catalog and by a real
  connection attempt;
- a tampered encrypted backup is rejected by authenticated decryption even when
  its outer manifest checksum is recomputed.

## Prerequisites

- Windows or Linux with PowerShell 7.4+, Docker with Compose and the repository
  `.env` plus `.local/secrets/` files created by `./scripts/dev.ps1 setup`.
- Pinned Dart 3.13.4 on `PATH` (the runner resolves the server lockfile with
  `dart pub get --enforce-lockfile`).
- The existing Docker Compose PostgreSQL service healthy. Start it with
  `./scripts/dev.ps1 db`; the runner requires it and never starts, stops or
  recreates it.
- Loopback port 8097 free for the isolated fixture API.

## Command

```powershell
pwsh ./scripts/backup/Run-BackupRestoreAcceptance.ps1
```

The runner exits non-zero on any failed step, names that step and writes the
sanitized report below. Failure log-tail redaction is not fully established; see
the diagnostic boundary below. It requires no parameters in normal use.

## Safety boundaries

- The normal StoreOS database (`STOREOS_DB_NAME`, default `storeos`) is never
  read, written, restored into, migrated or dropped. The runner only checks that
  it still exists after cleanup.
- The source database is `storeos_backup_accept_<run-id>` and restore targets are
  `storeos_restore_bkacc_<run-id>` (plus the corruption target ending in `c`).
  Every name is generated by the run and matches a strict pattern.
- Cleanup fails closed: a database is dropped only if it was generated by this
  run and matches the strict naming pattern. User-supplied database names are
  never dropped.
- `docker compose down -v` is never used.
- Owner and runtime credentials are read from existing secret files into
  process-local variables and excluded from the accepted JSON report. Do not
  treat the report's redaction checks as proof that every failure log tail is masked.
- Run-scoped backups and fixtures live under `.local/backup-acceptance/<run-id>/`
  and are removed after the run; only `report.json` remains.

## Report

`report.json` contains only non-sensitive metadata: run ID, timestamps, database
names (run-scoped), per-table counts and hashes, sequence state, revocation and
fencing booleans, the corruption result and cleanup status. The runner asserts
the report contains no database URLs, bearer tokens, password/token/secret/key
fields, private-key markers or known secret values before it is accepted; the
standalone regression is
[Test-BackupAcceptanceRedaction.ps1](../../scripts/backup/Test-BackupAcceptanceRedaction.ps1).

## Corruption test

The runner copies the encrypted backup, flips one byte in the ciphertext, and
rewrites only the outer manifest checksum so that superficial manifest
validation passes. It then invokes the real restore workflow and requires a
non-zero exit; the authenticated backup format rejects the stream. The
incomplete target database is dropped immediately and its removal is recorded.

## Cleanup

After success and after injected failures the runner verifies:

- this run's source and restore databases no longer exist;
- the normal StoreOS database still exists;
- the fixture API port is free;
- temporary manifests, backup files, verification results and fixture logs are
  removed (the sanitized `report.json` is retained).

If cleanup itself fails, the runner exits non-zero, records exactly which
resource could not be removed in the report and does not attempt broader
destructive cleanup.

## Failure injection (tests only)

`-InjectFailureAfter <none|prepare|backup|restore|verify|corruption>` aborts the
run after the named step to prove the cleanup guarantee. It is a test hook and
must not be used for production restores.

## Limitations

- The acceptance covers the bounded single-site employee journey and database
  evidence only. It does not back up or restore attachments, TLS material,
  configuration, plugin versions or external secrets, and it does not activate
  a replacement server or reconcile sync state.
- Restore revokes database sessions and plugin tokens, but the acceptance does
  not re-apply post-backup account revocations or deletions; that remains an
  operational responsibility described in the
  [deployment contract](../../docs/architecture/deployment.md).
- The run is destructive only to its own isolated databases; a host with an
  unhealthy Compose database fails before any change.

## Interrupted runs

An interrupted runner may leave its isolated databases behind. Every name is
listed in the run report. Verify the names begin with `storeos_backup_accept_`
or `storeos_restore_bkacc_`, confirm they belong to the interrupted run ID, then
remove only those databases through the Compose server. Do not drop the normal
StoreOS database and do not use `docker compose down -v`.

## Diagnostic and verification boundaries

The sanitized JSON report has explicit redaction assertions/tests. Backup/update
runner failure log tails are not masked like capacity diagnostics (L6/F13); no
actual disclosure was observed in the audit, but universal diagnostic secrecy
is not established. Fix this in a separate authorized harness change, and avoid
sharing raw failure tails without inspection. [Technical debt](../../docs/development/technical-debt.md)
tracks the open item.

This runbook documents commands, not a new acceptance run. The
[2026-10-04 audit](../../docs/development/project-health-audit-2026-10-04.md) did
not freshly rerun the full wrapper because it resolves dependencies. Restore
activation, post-backup access/deletion policy and off-host/RPO/RTO decisions
remain operator responsibilities.
